People & access · 01

Creating a user

Every person who needs to log in — internal staff or a client contact — starts here.

Sidebar→People→+ New user

Requires the user.create capability. If People isn't in your sidebar at all, ask an administrator to grant it.

  1. Fill in Username, name and email. Username is the only strictly required field.
  2. Set Role — this is what actually grants capabilities (see the note below). Team and Manager shape the org chart and reporting-line permission scopes.
  3. Set Customer if this person is a client-side contact rather than internal staff — it links them to that customer record, and both the bulk-import People sheet and the project participants picker use it.
  4. Description, Responsibility and Remark are free text for anyone looking the person up later — not shown to the person themselves.
  5. Save.
Role vs. capability

A Role is a bundle of capabilities (e.g. project.edit, timeline.view), each granted at a scope — own, team, or all. What a user can actually do, and on which projects, comes from their role and where they sit in the team/reporting structure — not from anything set on the user form itself. See Roles and Capabilities to inspect or change what a role grants.

Creating many people at once

Sidebar → Bulk import → People gives you a spreadsheet template with every one of these fields, including Role, Team, Manager and Customer as plain-text lookups by name. Upload it and you get a review screen — errors and warnings per row — before anything is actually saved. The combined template on the same page creates Customers, People and Projects from one workbook in a single pass, letting a new project's people reference a customer defined earlier in the same file.

People & access · 02

Managing passwords

There's no self-service "forgot password" flow. Every password is set by someone with edit rights on that account.

Setting a password when you create someone

On the New user form, Password is optional. What happens if you leave it blank depends on where you create the person:

Where you create themPassword left blank
Sidebar → People → New user No password set — they can't log in until someone edits them and sets one.
Project → People → Create a new person and add them Auto-generated — a random password is created and shown to you once, ready to hand off.
Bulk import → People sheet, Password column blank Auto-generated — shown per-row on the results screen after import.

If you want someone created from the plain People form to log in immediately, either type a password for them directly, or use the project-level "Create a new person" flow instead.

Changing an existing password

  1. Sidebar → People → open the person → Edit.
  2. Type a new value into Password. Leaving it blank here keeps whatever they have now — this is the one place the field's "leave blank" behaviour means keep, not skip.
  3. Save, and tell them the new password over a channel you trust — Planwise doesn't email it anywhere.

Getting an account

Accounts are created by an administrator (People, then New user). There is no self sign-up page.

  1. Your administrator creates your account and gives you a first password.
  2. Sign in with it. You are asked to choose your own password straight away: type it twice, in Password and Password confirmation.
  3. An admin can change your role, team or manager later from People.

Password rules

RuleExample that is refused
At least 6 charactersabc12
Not a common passwordpassword, 123456, qwerty
Both boxes must match (sign-up only)Typing a different value in Password confirmation

These rules are checked on the sign-up page. A password an admin types on the New user or Edit form is saved as entered and is not checked against them, so follow the same rules when setting one for someone else.

Changing your own password

Click Change password in the top bar. Type your current password, then the new one twice. The same rules apply (at least 6 characters, not a common password). You stay signed in afterwards.

First sign-in: set your own password

Every account is asked to change its password once: everyone who existed when this was switched on, and every account created since (People → New user, Bulk import, a project's "create person", or sign-up). Until you do, any page you open takes you to Change password; Sign out still works. After that you're never asked again — not even when an admin later sets a new password for you.

Showing the password while typing

The password boxes on the login and sign-up pages have an eye button on the right. Click it to show what you typed, and click again to hide it. Use it to check for typos, not on a shared screen.

No self-service reset

There's currently no "forgot my password" page. If someone is locked out, an admin (or anyone with user.edit reaching that account) has to set a new one for them via Edit.

Organisation · 03

Creating a customer

A customer is the client organisation a project is delivered for. Projects, client-side people, and the BRD's stakeholder section all hang off this record.

Sidebar→Customers→+ New customer

Requires customer.manage.

  1. Name is the only required field. Code is a short key (like ACME) — leave it blank and one is generated from the name automatically.
  2. Account manager and Primary contact are picked from existing users — create those people first if they don't exist yet.
  3. Fill in industry, website, contact details and notes as you have them — all optional, all editable later.
Creating many customers at once

The same Bulk import tool has a Customers template and a combined workbook that creates customers, their projects, and their people in one upload — each sheet can reference records defined earlier in the same file, even before they exist in the database.

Organisation · 04

Putting people on a project

Every project keeps two rosters — client side and our side — each person carrying a role, responsibility and remarks that the BRD agent reads directly.

Project→People tab

Adding, removing or editing briefs needs project.edit on that specific project (see the note below). Everyone with view access can see the roster either way.

Add someone who already has an account

  1. Click + Add existing user (top right, or the card at the bottom of the page).
  2. Pick the person, set their Side (client or our organisation), Position on this project, and optionally a role description, responsibility and remarks.
  3. Mark Is primary contact if they're the one point of contact for their side.

Add someone brand new

Click + New person instead — this creates the user account and adds them to the project in one step. See Managing passwords for what happens to the password field here.

Move someone between sides

Once someone's on the roster, just drag their card from one column to the other — the switch saves immediately, no form needed. On a touchscreen, tap the card once to pick it up, then tap the other column to drop it.

If "Add someone" is missing

That section only renders when you hold project.edit on this project. A role can have that capability at team scope, which only applies if the project is assigned to your team or you own it — a project with no team and a different owner won't grant access even to an otherwise senior role. An administrator can fix this by setting the project's team, its owner, or by widening the role's scope to all.

Capturing work · 05

The timeline: notes, audio and documents

Everything that happens on a project — a note, a meeting recording, a spec someone emailed over — goes on the timeline. It's the raw material both AI agents read from.

Project→Timeline tab

Adding entries needs timeline.add; reprocessing or renaming speakers needs timeline.process.

A typed note

Pick a Kind (Note, Meeting, Decision, Change request…), type into Body, and click Queue entry. It goes into the AI queue: the page shows your place in line and roughly how long it will take, and you get a notification when it's done. Leave Include in BRD checked if this should feed the next BRD regeneration.

An audio recording

Attach a .wav, .mp3, .m4a, .ogg or similar file. Planwise runs it through a pipeline automatically:

  1. Noise reduction — the recording is denoised before anything else touches it.
  2. Transcription — speech-to-text via the configured ASR model.
  3. Diarization — separates the recording into speaker turns (SPEAKER_00, SPEAKER_01, …).

Once it's done, open the entry and name each speaker — type a name, or map them to an existing project participant. This isn't cosmetic: search and Ask AI both use the name you give here, so "what did the client say about budget" only works well once speakers are named.

A document — PDF, Word, or PowerPoint

Attach a .pdf, .docx or .pptx and Planwise extracts its text straight into the entry — paragraphs and tables from Word, slide text and tables from PowerPoint, page text from PDF. Plain text formats (.txt, .md, .csv, .json, .srt, .vtt) are read as-is.

Scanned PDFs

Extraction reads the text layer of a PDF — a scanned image with no embedded text won't produce anything, and the entry's processing log will say so plainly rather than silently leaving it blank.

The AI layer · 06

The BRD agent

An LLM reads everything on the timeline and drafts the Business Requirement Document for you — then keeps it in sync as new entries come in.

When it writes automatically

Right after a timeline entry finishes processing — if Include in BRD was checked — the agent folds it into the document and produces a new version. For audio entries, this happens once every speaker has been named, since the agent needs to know who said what first.

Updating it by hand

Project→BRD tab

  • Regenerate — shows how many entries haven't been folded in yet; click to pull them all in and produce a new version.
  • Edit — hand-edit the current version directly, for wording the agent won't get right on its own.
  • History / Compare — every regeneration is a new numbered version; compare any two to see exactly what changed.
  • Download .md — export the current version as plain Markdown.

Requires brd.view to read it, brd.generate to regenerate, and brd.edit to hand-edit.

The AI layer · 07

Ask AI

A chat assistant scoped to exactly one project — it can search that project's documents, query its structured data, or both, and it streams its answer back live.

Project→Ask AI tab

Requires timeline.view on the project — the same permission that gates the timeline itself.

The two switches

ToggleWhat it doesBest for
RAG (documents) Semantic search over notes, meeting transcripts, uploaded document text, and the BRD. "What did we decide about X", "what does the BRD say about scope"
DB agent (structured data) Writes and runs a read-only query against this project's tasks, people, customer and project facts. "Who's on the client side", "what's still open", "what's the budget"

Leave both on and the assistant picks whichever a question actually needs — many questions use both in one answer. Turn one off to restrict it on purpose; turn both off for a plain conversational reply with no lookups.

Reading the answer

  • Text streams in as it's generated, formatted as markdown — tables, bold, lists all render properly.
  • Citation chips under an answer name exactly which document, task, or person record it drew from.
  • SQL used, when the DB agent ran a query, is an expandable disclosure — the exact statement it executed, nothing hidden.

Keeping it current

  • ↻ Refresh index rebuilds the document search index on demand — normally automatic after new timeline content or a speaker rename, this is the manual fallback.
  • 🗑 Clear chat wipes your own conversation history for this project. It doesn't touch anyone else's, and it doesn't touch the underlying documents or data.
Strictly one project at a time

The assistant can only ever see this project's own data — not just by instruction, but structurally: the underlying tools have no parameter through which a different project could even be named, and the database role behind the "DB agent" can only read a handful of views that are already filtered to this project before your question ever reaches them.

Why does it sometimes say "SPEAKER_01" instead of a name?

If a diarized speaker on an audio entry hasn't been named yet (see The timeline), the assistant reports them by their raw label rather than guessing who they might be. Name the speaker on the entry page and ask again — the index picks up the change automatically.

Working with tickets · 08

Raising a good ticket

A ticket is only as useful as what you put in it. Whoever picks it up — a person or an agent — can only act on what's written down; they can't see your screen, your browser tab, or what you tried first.

Sidebar→Tickets→+ New ticket ·or from a project's Tickets tab

Requires ticket.create. If you land here from a project, that project is filled in for you automatically.

Before you even open the form

The New ticket page shows a one-time popup — "Before you raise this ticket" — that covers when a ticket needs UI/UX Team approval first:

  • A small change to an existing page (text, alignment, spacing, colour, icons) — raise the ticket directly, no design approval needed. Just include the page's URL (see below).
  • A new page/screen, or a significant UI/UX change — raise a ticket to the UI/UX (Designer) Team first. Only once that design is reviewed and approved should you raise the Development ticket.
  • Non-UI work (backend logic, data, infra, a question) — raise the Development ticket directly.

Fill the form out fully

  1. Type — Bug, Change request, Feature request, Task, Question or Incident. This decides whether the Bug/incident detail section below even matters.
  2. Title — one line that names the actual problem, not just the symptom. "Save button on the invoice form does nothing after a discount is applied" beats "Save doesn't work".
  3. Team — narrows who shows up in Assignee to that team's members. Set this before picking an assignee, not after.
  4. Priority (and Severity, for a bug or incident) — how urgent, and how bad the impact is if it's not fixed.
  5. Due date — optional, but worth setting if this is blocking something with a real deadline.
Write the description like the reader has never seen your screen

Because they haven't. The single biggest thing that makes a ticket fast to solve — by a person or an AI agent — is giving it everything it would otherwise have to come back and ask you for.

What a complete description includes

Include thisWhy it matters
The exact page URL where the issue happens or the change is needed Saves the reader from hunting for the right screen — paste it straight from the browser's address bar, e.g. https://planwise.augtrans.com/projects/79/edit/. For an app-wide or non-UI issue, say so instead of leaving it blank.
What you did, step by step, in order "Click X, then Y, then Z" reproduces the exact conditions instead of leaving the reader to guess a path that happens to trigger it. Bug and incident tickets have a dedicated Steps to reproduce field for this — use it.
What you expected vs. what actually happened Also dedicated fields (Expected result / Actual result) on bug and incident tickets. Stating both removes any ambiguity about what "fixed" even looks like.
Environment — browser, OS, app version, account/role you were using A lot of bugs are specific to one browser, one role's permissions, or one screen size. Without this, the reader may not even be able to reproduce it.
A screenshot or screen recording Attach it rather than describing a layout or an error banner in words — a picture of the exact state of the page removes a whole round of back-and-forth. See Attachments below.
Anything you already tried Stops the reader from re-treading a workaround or a fix you already ruled out.

Attachments — screenshots, logs, recordings

The form's Attachments field on the New ticket page takes up to 10 files, 10 MB each. Anything relevant helps: .png / .jpg / .gif / .webp / .svg screenshots, .mp4 / .mov / .webm short screen recordings, .log / .txt / .csv / .json / .har for errors or network traces, or a .pdf. On an existing ticket, uploading more attachments adds to what's already there rather than replacing it.

Good vs. thin

Thin: "Login page is broken."
Good: "On /login/, entering a correct username/password and clicking Sign in shows a spinner forever and never redirects (Chrome, Windows). Expected: redirect to the dashboard. Tried a hard refresh and an incognito window — same result both times. Screenshot of the stuck spinner attached, plus the failed request from the browser console."

Why this matters more than it looks like

A ticket with a URL, clear steps, expected/actual behaviour and a screenshot can often be acted on immediately — no clarifying questions, no waiting on you to reply. A ticket that just says something is "broken" or "needs fixing" usually comes back to you for the details above before any real work can start — whether the person picking it up is on the team or an AI agent reading the ticket.
