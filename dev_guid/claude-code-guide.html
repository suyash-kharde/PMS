00How the pieces connect

Claude Code runs on the developer's laptop. Everything else — Planwise, Penpot, and both MCP servers — runs on the server at 172.16.16.214. The laptop talks to two independent MCP endpoints; a browser tab on the laptop carries the Penpot design canvas.

What each server gives you

ServerScopeAuthYou get
planwise
one per project
 Exactly one Planwise project. A token cannot reach another project even if you can. Secret token in the URL, shown once. Bound to the person who created it — every call runs as them and respects their capabilities. Project overview, the BRD and standards docs, semantic search, a read-only SQL agent, tickets, requirements & field specs, test cases, the dev log, and the Penpot file id.
penpot
shared, one instance
 Whatever design file is open and bridged in the Penpot editor tab. A per-account MCP key from Penpot's Settings → Integrations. In --multi-user mode the key pairs the Claude Code session with the editor tab that Connected with the same key. execute_code against the open file, a high-level API overview, type reference, and shape export.

0Before you start

  • You need the mcp.manage and penpot.manage capabilities on the project — that is Team Lead, Project Manager, Director or Administrator.
  • The Penpot design workspace is provisioned automatically by the background worker when the project is created (a bot account, its own team, and a starter file). If the project pre-dates the integration, open the Design tab once and it will provision.
  • Claude Code on the laptop must be able to reach 172.16.16.214 on ports 443 (Planwise) and 9001 (Penpot). The laptop's browser needs the same.
  • Real speaker diarization on audio uploads needs an HF_TOKEN set on the server; without it, transcripts still work but speaker turns are approximate.

Part AWire Claude Code to the project

Eight steps. Steps 1–4 happen in Planwise, steps 5–7 in Penpot, step 8 back in the terminal. Do them once per project per developer.

1
Open the project and go to the Claude Code tab

From Projects, open the project. The tab strip runs along the top of the project page; scroll it right and pick Claude Code.

2
Fill the form and press Create link

Give the link a name that says whose laptop it is. Leave both write boxes off for a read-only link; tick one only if this developer should be able to change tickets or requirement status from the terminal. Writes still require the underlying capability on your own account.

3
Copy the link — it is shown once

A panel drops in with the full URL and a ready-made claude mcp add command. Copy it now. Planwise stores only a hash; there is no way to see the token again. If you lose it, revoke the link and make a new one.

4
Open the Design tab

Back on the project, scroll the tab strip to Design. If the workspace is ready you will see the buttons below. Open in Penpot (edit) takes you into the design file — you will need it open in the browser for step 7.

5
In Penpot, enable the MCP server and generate a key

The Penpot editor from step 4 is where the design gets built. Its MCP server is a shared service on this box (nginx already proxies it), but it runs in --multi-user mode, so it needs a per-account MCP key. In Penpot: avatar (top-left) → Settings → Integrations → MCP Server. Flip Status to enabled, then Generate MCP key.

What the key is for
The MCP server pairs your Claude Code session with your Penpot editor tab by matching this key on both sides. One key per developer per Penpot account; set an expiry if you want. Regenerating it revokes the old one immediately.
Admin shortcut. Each project's Penpot workspace already has a bot access token that the server accepts as a userToken. From the Planwise host: docker exec pms_web python manage.py shell -c "from apps.penpot.models import PenpotWorkspace; print(PenpotWorkspace.objects.get(project__key='DDMS').access_token)" — use that string in place of <MCP-KEY>, and sign in to Penpot as that bot for step 7.
6
Build the .mcp.json on the laptop

The Design tab's Connect Claude Code to this design card shows the skeleton with both servers. Copy it to the Claude Code laptop (which must be able to reach 172.16.16.214), swap <claude-code-token> for the Planwise token from step 3, and paste the Penpot userToken from step 5.

{
  "mcpServers": {
    "planwise": {
      "type": "http",
      "url": "https://172.16.16.214/mcp/pwmcp_ev_Fn6…NbMIw/"                 ← token from step 3
    },
    "penpot": {
      "type": "http",
      "url": "http://172.16.16.214:9001/mcp/stream?userToken=<MCP-KEY>"   ← the key from step 5
    }
  }
}
Not any string
Earlier setups let you invent the userToken. This instance is --multi-user: the value must be a real Penpot MCP key (step 5) or it is rejected with No userToken found in session context.
7
In the Penpot editor, connect MCP for this file

Open the design file (step 4) as the account whose key you generated. In the editor's header menu (≡) → MCP server → Connect (there is also an MCP button on the toolbar). Penpot loads its own MCP plugin, hands it your key, and opens the bridge — you'll see “MCP is now active in this tab.” No manifest URL, no manual install.

Possible warning
The plugin may report “Version mismatch: server built for Penpot 2.16.0, this instance is 2.16.x.” It still works; mention it first if a call misbehaves.
Same account both sides
The bridge uses the key of whoever is signed in to this Penpot tab. If that isn't the same key that's in .mcp.json, Claude Code's execute_code / export_shape fail with No plugin instance connected for user token.
8
Confirm in Claude Code

Add the servers (or drop the edited .mcp.json in the project root) and run /mcp. Both should be connected.

$ claude mcp add --transport http planwise-ddms https://172.16.16.214/mcp/pwmcp_ev_…/
Added HTTP MCP server planwise-ddms
$ claude
> /mcp
  planwise-ddms   connected   28 tools · 6 resources · 2 prompts
  penpot          connected   4 tools
> use get_design_workspace to find this project's Penpot file, then
  read the tech_stack and dev_instructions docs before you build anything.
First move, every session: call project_overview, then get_document for tech_stack and dev_instructions. Those define the stack and coding standards this project is built to — skipping them means rework.

Part BUse each component

Every component below has a web side (for people) and an MCP side (for Claude Code). They read and write the same data — a bug you file from the terminal shows on the Tickets board a second later.

Project context & standards docs

Tech Stack · Dev Instructions · Build Plan tabs

Four documents ground everything: Tech Stack and Dev Instructions (the org defaults until a project overrides them), Build Plan, and the BRD. Each can be frozen once final. Claude Code reads them as markdown; people edit them on the tabs.

From Claude Code
  • project_overview — status, people, counts, which docs exist
  • get_document(kind) — tech_stack, dev_instructions, build_plan, brd
  • get_design_workspace — the Penpot file id + URL for this project
  • Resources: planwise://project/overview, …/doc/tech_stack, …/brd, …/design

Ask AI & the data agent

Ask AI tab

One agent with two switchable tools: RAG (semantic search over notes, transcripts, uploads and the BRD) and a read-only SQL agent scoped to this one project through a locked-down database role. The chat shows its sources and the exact SQL it ran.

From Claude Code
  • search_docs(query, limit) — snippets, cheap, use often
  • ask_project(question, use_docs, use_data) — synthesised answer with sources
  • query_data(sql) — one read-only SELECT against 6 project-scoped views; cannot see other projects or base tables
Rough guide: search_docs for text you would recognise, ask_project when the answer needs joining several sources, query_data for counts and rollups.

Timeline → BRD

Timeline & BRD tabs

Anything that happens on the project goes on the Timeline — a typed note, a dropped document, or an audio/video recording. Audio is denoised, diarized and transcribed; you name the speakers; then the LLM rewrites the whole BRD as a new immutable version with each requirement attributed to the person who raised it.

Claude Code reads the BRD, never writes it. Use get_document("brd") or the planwise://project/brd resource. The BRD is regenerated only from timeline input, by the LLM, on the server.

Tickets

Tickets tab · /tickets/

Bugs, change requests, incidents and questions, on a triage lifecycle (new → triaged → accepted → in_progress → resolved → closed) that is deliberately separate from the delivery board. Keyed per project: DDMS-1, DDMS-2…

From Claude Code
  • list_tickets — filter by status / type / assignee / text
  • get_ticket(ref) — full detail, comments, history, attachments
  • write comment_ticket(ref, body)
  • write set_ticket_status(ref, status, resolution)
  • write create_ticket(title, type, …) — file a bug you found
  • Prompt: fix_bug(ticket) — loads the ticket + the standards docs
Writes need both the link's ticket writes scope and your own capability (ticket.comment / ticket.triage / ticket.create).

Requirements & sprints

Sprints & Requirements tabs

A requirement carries the whole build contract: a user story, acceptance criteria (plain statements or Given/When/Then), field specs (name, type, mandatory rule, length, validation), unit test cases, risks and dependencies. Sprints are time-boxed sets of requirements. An AI planner can draft the lot from the BRD and standards docs.

Read
  • list_sprints / get_sprint(number)
  • list_requirements — by sprint / status / text / backlog
  • get_requirement(number) — criteria, field specs, tests, deps
  • list_test_cases / get_test_case(number)
  • list_external_services — Stripe, SMTP, client data… and readiness
Write sprint writes + capability
  • set_requirement_status(number, status) — move to in_review when the design is done
  • record_test_result(number, status, …)
  • add_acceptance_criterion(…) — if the design surfaced a state nobody specified
  • Prompt: implement_requirement(requirement)

Dev Log

Dev Log tab

Where Claude Code reports its own progress — what it built, how far along, which milestone it reaches. Milestones are free-text; the tab rolls them into an "N of M complete" bar. People can add updates by hand too.

From Claude Code
  • list_dev_milestones — call first so labels stay consistent
  • push_dev_update(headline, status, milestone, …) — links to a sprint / requirement / ticket / task
  • update_dev_update(id, status, milestone_done) — flip to completed
  • list_dev_updates / get_dev_update(id)
Available on any link — it only ever writes to the dev log, so no write scope is needed.

Generate UI in Penpot & verify visually

Design tab · Penpot editor

This is the whole point of connecting both servers: Claude Code pulls the spec from Planwise, draws the screen in your Penpot file with execute_code, checks its own work against the acceptance criteria with export_shape, you glance at the browser to approve, and only then does it move on to writing the component.

Does the MCP help?
Yes — without it there is no path from a Planwise requirement to a Penpot canvas. The penpot server's execute_code is the drawing hand; export_shape is how Claude Code sees what it drew; the planwise server's get_requirement is the checklist it grades against.

The loop

Verifying visually — two channels

A real session

> Read DDMS-R7 and the tech_stack doc. Confirm the open Penpot file is "DDMS — UI".
  planwise: get_requirement("DDMS-R7") · get_document("tech_stack") · get_design_workspace
  penpot:   execute_code("return penpot.currentFile.name")  → "DDMS — UI"  ✓

> Build the Add Participant board: PrimeNG-style form, every field from the field
  spec, mandatory markers, the client/internal side as a segmented control.
  penpot: high_level_overview · penpot_api_info("Board") · execute_code(… createBoard, addFlexLayout …)
  penpot: export_shape(board)  → checks C1–C4 · C3 fails · fixes · re-exports
  "Board ready. 4/4 criteria. Empty + filled + invalid-email states. Take a look?"

> [you look at the browser tab] The segmented control should sit above Email, not below.

> [fix, re-export]  approved

> Set DDMS-R7 to in_review, log it, then generate the Angular component + template
  from this board, following dev_instructions.
  planwise: set_requirement_status("DDMS-R7","in_review")
  planwise: push_dev_update("Add Participant form designed & approved",
                            requirement="DDMS-R7", milestone="Participant management")
  … writes add-participant.component.ts / .html …

> push a dev update when it compiles.
  planwise: push_dev_update("Add Participant component built", status="completed", …)

Then proceed to the next step

Approval is the gate between design and code. Once you have looked and said yes:

  • Mark the requirement — set_requirement_status("DDMS-R7", "in_review") (or ready if it was still draft).
  • Log the milestone — push_dev_update(…, milestone="…") so the Dev Log shows design is done and code is next.
  • Generate the component against dev_instructions (Angular + PrimeNG here). Claude Code can read the board's structure and Penpot's own CSS export to keep the markup faithful.
  • Close the loop — another push_dev_update when the code compiles, and record_test_result as you write the unit tests from the acceptance criteria.
Not headless. If execute_code or export_shape hangs, the design file is not open in the browser or the MCP bridge dropped. Re-open the file (step 4) and re-connect via Menu → MCP server → Connect (step 7). Build one board at a time and export after each — a single giant execute_code that half-works is hard to unpick.

AI model configuration

AI models · Model services (admin)

Every endpoint the system calls — the LLM that writes the BRD, the ASR endpoint, embeddings, the reranker — is a row you edit in the UI, with its own key and CA certificate. Changes take effect on the next call, no redeploy. Model services is the live health page. Claude Code does not touch this; it is admin territory.

A write tool returns "Permission denied: your account lacks …"The link's owner does not have that capability on this project. A Director/Admin grants it, or a different person mints the link.
